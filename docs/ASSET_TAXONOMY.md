# Asset taxonomy — 2D game graphics in VPE565

Reference for deciding **what an image is for**, **where it lives on disk**, and
**whether VXP Pixel Editor can represent it at all**. Every family below is
generated by `tools/make_samples.py` into `Documents\VPE Pixel\`, so the folder
layout in §4 is not aspirational — it is what the sample library actually
contains and what the gallery scans.

---

## 1. Two 2D genres, two asset shapes

### 1A. Top-down / isometric (RPG, farming sim, RTS, dungeon crawler)

Everything is read from above, so a tile must **self-tile** and a character must
be legible from four angles.

| Group | Folder | Contents | Sample prefix |
| --- | --- | --- | --- |
| Terrain | `tile/topdown/terrain/` | grass, dirt, sand, snow, rock, water (deep + shallow), swamp, lava — each seamless | `td_<name>` |
| Roads & edges | `tile/topdown/roads/` | dirt path, asphalt, wooden bridge, shore, cliff edge, rail | `td_<name>` |
| Architecture | `tile/topdown/architecture/` | brick / wood / stone walls, roof, window, door (closed + open), stairs, fence, pillar | `td_<name>` |
| Interior | `tile/topdown/interior/` | wood + tile floors, carpet, bookshelf, table, chair, bed, torch, spikes, fireplace | `td_<name>` |
| Flora & props | `tile/topdown/flora/` | bush, flowers, rock, stump, barrel, pot, gravestone | `td_<name>` |
| Characters | `sprite/characters/player/` | 4 directions × 12 actions (idle, walk, run, attack, cast, hurt, die, pickup, push, dig, water, fish) | `td_hero_<dir>_<action>_<frame>` |
| Enemies / NPCs | `sprite/enemies/` | goblin, skeleton, orc, zombie, villager, merchant, dragon | `td_<name>_<frame>` |
| Item icons | `sprite/items/icons/` | bow, staff, helmet, armor, boots, potion, wood, meat, ore, gold | `ic_<name>` |
| HUD | `sprite/ui/hud/` | cursor, button, slot, HP bar, MP bar (flat singles — for a full state machine see §1C) | `hud_<name>` |
| Particles | `sprite/vfx/particles/` | dust, slash, magic bullet, sparkle | `fx_<name>_<frame>` |
| Skill effects | `sprite/effect/` | fireball, explosion, lightning, cast circle, ice shards, poison cloud, heal sparkle (`.vpea`, 32×32) | `fx_<effect>.vpea` |
| Hero scenes | `sprite/characters/player/` | the same top-down hero as playable animation: 4 directions × 7 actions (idle, walk, run, attack, cast, hurt, die), 116 frames (`.vpea`, 16×16) | `hero_<dir>_<action>.vpea` |
| Boss scenes | `sprite/enemies/boss/` | five 3-tile bosses, 40 actions / 188 frames (`.vpea`, 48×48) | `<boss>_<action>.vpea` |

The farming actions (`dig`, `water`, `fish`, `pickup`) exist because the genre
pairs a top-down map with a tool belt — a walk cycle alone is not enough to
drive that kind of game.

The dragon runs idle / walk / fly / bite / breath / slam / hurt / die (36 frames),
the stone golem idle / walk / roar / slam / boulder / beam / hurt / die (38), the
slime king idle / hop / slide / attack / split / spit / hurt / die (36), the ice
wizard idle / walk / cast / bolt / blizzard / freeze / hurt / die (40) and the
sand scorpion idle / walk / sting / pinch / venom / burrow / hurt / die (38). All
five share the 48×48 canvas and the same rim colour, and never share a
silhouette: the golem, the wizard and the slime are upright masses, the dragon is
a winged quadruped, and the scorpion is the only low, wide, eight-legged shape —
the one whose attacks leave through the right column while its tail works the
upper left.

### 1B. Side-scroller / platformer

Read from the side, so tiles carry a **visible top surface** and the background
is built from independently scrolling layers.

| Group | Folder | Contents |
| --- | --- | --- |
| Platforms | `tile/side/platform/` | ground top, left/right corners, floating block, ice, mud, conveyor (2 frames) |
| Hazards | `tile/side/hazard/` | spikes, spinning saw (2 frames) |
| Parallax | `texture/background/parallax/` | sky, far clouds, mid mountains, near forest, night — drawn wide (240 px) so they repeat horizontally |

Corner tiles matter more here than anywhere else: a platformer map is 90 %
`ground_top` plus the two corner variants, and missing corners is the single
most common reason a hand-made tileset looks wrong in game.

### 1C. UI widgets (menus, dialogs, keypads, HUD chrome)

Buttons are the one family that is **state-indexed rather than frame-indexed**:
an engine swaps `normal → press → focus → off` at the same coordinates, so every
state of a shape must share one canvas size, and the sprite must survive being
painted over any background. That rules out the flat `sprite/ui/hud/` singles and
gives a dedicated tree:

| Group | Folder | Contents |
| --- | --- | --- |
| Pressable widgets | `sprite/ui/buttons/` | 3 styles × 9 shapes × 4 states, plus toggle / checkbox / radio in on + off |

| Key | Meaning |
| --- | --- |
| `btn_<style>_<shape>_<state>.vpe` | one widget state, e.g. `btn_retro_wide_focus.vpe` |
| style | `retro` (VQEAF OS Retro Utility handset), `cream` (VQEAF OS Claude S40 Day), `arcade` (top-down game green, same tokens as `hud_button`) |
| shape | `wide 96x24`, `std 72x20`, `small 48x16`, `soft 80x22`, `key 28x28`, `round 32x32`, `icon24`, `icon36`, `tab 64x18` (top corners only) |
| state | `normal`, `press`, `focus`, `off`; the three marks use `on` / `off` |

Two invariants make the set usable, both asserted by `test_button_family()`:

- **A 3 px transparent margin on every canvas.** The rim costs 1 px, the focus
  halo costs 1 px further out, and the pressed label needs a pixel to travel
  down into. Without the margin, `focus` would be a larger sprite than `normal`
  and swapping states would jitter the layout.
- **No token may pack to `0xFFFF`.** The cream style's panel colour *is* white in
  `Theme.h`, so it is re-authored as `(255, 252, 240)`; `pack()` refuses the key
  outright. See §3 rule 1.

## 2. 3D PBR texture maps — explicit non-goal

The source taxonomy lists albedo, normal, roughness, metallic, AO, height and
emission maps for PBR materials. **VPE565 cannot store these.**

RGB565 packs three quantised colour channels into 16 bits per pixel:

| Map | Needs | Possible in VPE565? |
| --- | --- | --- |
| Albedo / base colour | 3 colour channels | Yes — this is exactly what VPE565 is |
| Emissive | 3 colour channels | Yes, as a plain colour texture |
| Roughness / metallic / AO / height | one float per pixel, linear | No — 5/6-bit quantisation destroys the range, and the editor offers no linear (non-sRGB) workflow |
| Normal | signed X/Y/Z, usually 2–3 channels | No — the encoding is lossy and there is no way to flag the file as linear data |

So the editor's texture category (`texture/`) means **albedo / background /
UI-panel art**, nothing more. Do not generate fake PBR maps to fill out a
folder tree: a 565 "normal map" decodes to a visibly banded vector field and
breaks lighting in every engine that trusts it. Author the albedo here and the
rest of the stack in a tool that handles 16-bit-per-channel linear data.

## 3. Style rules that the format enforces

These are not taste preferences — the encoder makes the alternatives impossible
or wrong.

1. **`0xFFFF` is transparency, not a colour.** The gallery keys RGB565 white out
   of `sprite` and `tile` thumbnails. A solid tile that accidentally contains
   white pixels renders with holes. Encoding makes `0xFFFF` out of any colour
   with `r ≥ 248`, `g ≥ 252` **and** `b ≥ 248`, so a generic "brighten" pass can
   hit it by accident: `rgb(246, 252, 255)` plus 3 on each channel saturates to
   `rgb(255, 255, 255)` → `0xFFFF`. `safe_light()` caps every channel at 247,
   which keeps the red field below full and makes the collision impossible.
2. **Palette is 565-wide whether you plan for it or not.** Every colour is
   quantised on save, so author with an explicit small palette (`mix()` of a few
   base colours) instead of letting the encoder dither 200 near-identical greys.
3. **One outline colour per family.** The samples share a single dark rim
   (`outline()`), which is what makes 250 unrelated procedurally drawn assets
   read as one art set.
4. **Fixed frame counts.** Inside one atlas family the loop lengths are identical
   (walk 4, run 2, idle 2, single-shot actions 1–2); the animated knight set ships
   as `.vpea` and is not atlas-packed — idle 4 / walk 4 loop, attack 8 / block 3 /
   skill 6 play once. The `sprite/effect/` library follows the same rule per scene:
   5–8 frames each with its own `loop` flag, so one effect is one family and never
   a mixed row. `sprite/characters/player/` fixes its counts per action across all
   four directions (idle / walk / run / attack 4, cast / die 5, hurt 3), so an
   engine can index a direction without special-casing frame counts. The five bosses
   in `sprite/enemies/boss/` are one file per action and obey the same contract:
   idle 4, locomotion 4 (walk / fly / hop / slide), hurt 3, one 5-frame strike
   (slam / cast / split / sting), the remaining two attacks and die 6 — dragon 36,
   golem 38, slime 36, wizard 40, scorpion 38 frames. Every frame is the 48×48
   canvas, which is 3 tiles wide on purpose so a boss cannot be packed into a
   character atlas.
   Frames must
   be the same dimensions or the atlas packs them wrong.
5. **Determinism.** Generation is seeded per asset name; never salt with
   `hash()`, which is randomised per process and would reshuffle the library on
   every run.

## 4. Folder layout

The canonical tree from the source document maps onto the editor's fixed
category roots like this:

| Source document path | VPE Pixel path |
| --- | --- |
| `sprites/characters/player/idle.png` | `sprite/characters/player/td_hero_down_idle_0.vpe` |
| `sprites/items/` | `sprite/items/icons/` |
| `vfx/particles/` | `sprite/vfx/particles/` |
| `vfx/effects/` (subject-independent) | `sprite/effect/` |
| `tilesets/topdown/terrain/` | `tile/topdown/terrain/` |
| `tilesets/platform/` | `tile/side/platform/` |
| `textures/backgrounds/parallax/` | `texture/background/parallax/` |
| `textures/ui/` | `sprite/ui/buttons/`, `sprite/ui/hud/` |
| `textures/pbr_materials/**` | — not supported, see §2 |
| `titlesets/` | `titleset/` |

Notes:

- `sprite`, `texture`, `tile`, `titleset` are the four roots the editor creates
  and the only names `asset_kind()` recognises. Anything below them is free-form
  grouping.
- `asset_kind()` walks `path.parents`, so `sprite/characters/player/x.vpe` is
  still a sprite; `MAX_SCAN_DEPTH = 4` covers `root → category → group → sub-group`.
- Project folders (e.g. `PuzzleField/`) sit beside the category roots and keep
  their files flat — a project is a working document, not a library entry.
- Animations use the `.vpea` container and keep one file per action, named
  `<subject>_<action>.vpea`: `sprite/characters/knight/knight_attack.vpea`,
  `sprite/characters/knight/knight_idle.vpea`. Where a facing direction changes
  the drawing, the direction goes in the name: the playable hero ships 28 scenes
  as `sprite/characters/player/hero_<dir>_<action>.vpea` beside the flat
  `td_hero_*` stills it reuses the body from. Enemies that need their own silhouette
  live one folder down in `sprite/enemies/boss/<boss>_<action>.vpea` — `dragon_`,
  `golem_`, `slime_`, `wizard_`, `scorpion_` — next to the flat `td_<name>_*.vpe`
  stills. Reusable effects live under
  `sprite/vfx/<subject>/fx_<effect>.vpea` so an engine can layer them on any
  character - `sprite/vfx/knight/` holds the knight's own slash arc, shield
  flash and shockwave. A subject-independent effect library goes one level
  higher in `sprite/effect/fx_<effect>.vpea` (fireball, explosion, lightning,
  cast circle, ice shards, poison cloud, heal sparkle), and its exports land in
  `exports/effect/`. The gallery reads frame 0 for the thumbnail and shows `· 8F`.

## 5. Regenerating and consuming

```
python tools/make_samples.py            # 285 game-art assets
python tools/make_vqeaf_icons.py        # 24 VQEAF OS system icons
python tools/make_ui_buttons.py         # 126 pressable-widget states (§1C)
python tools/make_knight_anim.py        # 8 .vpea animations + 1 .vpe still + review sheets
python tools/make_effect_anim.py        # 7 reusable .vpea effects -> sprite/effect + exports/effect
python tools/make_player_anim.py        # 28 .vpea hero scenes (4 directions x 7 actions) -> sprite/characters/player
python tools/make_dragon_anim.py        # 8 .vpea boss scenes (36 frames, 48x48) -> sprite/enemies/boss
python tools/make_golem_anim.py         # 8 .vpea boss scenes (38 frames, 48x48) -> sprite/enemies/boss
python tools/make_slime_anim.py         # 8 .vpea boss scenes (36 frames, 48x48) -> sprite/enemies/boss
python tools/make_wizard_anim.py        # 8 .vpea boss scenes (40 frames, 48x48) -> sprite/enemies/boss
python tools/make_scorpion_anim.py      # 8 .vpea boss scenes (38 frames, 48x48) -> sprite/enemies/boss
python tools/make_fnynn_map.py          # 92 Fnynn assets (15 tiles + 77 sprites) -> fnynn_map/{tile,sprite} + sheets
python tools/make_fnynn_anim.py         # Fnynn .vpa action strips for the same rigs
python tools/play_animations.py         # play every .vpea through the editor, export preview GIFs
python test_smoke.py                    # format + gallery + tool + widget checks
python .qoder/skills/vpe-game-assets/scripts/vpe_tool.py atlas \
    --dir "Documents/VPE Pixel/sprite/characters/player" \
    --out player.png --json player.json --transparent-white
python .qoder/skills/vpe-game-assets/scripts/vpe_tool.py atlas \
    --dir "Documents/VPE Pixel/sprite/ui/buttons" \
    --out buttons.png --json buttons.json --transparent-white
```

The generators are deterministic and only write files whose names they own, so
hand-made art in the same tree survives a re-run. `PuzzleField/` is a saved
sample *project* (18 files), not generator output — it sits beside the category
roots to show what the editor's own save layout. `fnynn_map/` is the same kind of
project folder: one external game (`Fnynn`, 240×320 software-RGB565 MRE handset)
consumes its PNGs directly through that game's own `png -> RGB565+mask .raw`
packer, so the set stays flat and name-bound rather than moving into
`sprite/`/`tile/`.
